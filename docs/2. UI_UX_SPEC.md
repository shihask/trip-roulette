# Trip Roulette Kerala --- UI/UX Specification

**Document version:** 1.2 (routes updated)\
**Date:** 4 November 2026\
**Status:** Design baseline; visual design and usability testing pending

------------------------------------------------------------------------

## 1. Design goals

The interface should make travel discovery feel exciting while keeping
decisions understandable and trustworthy.

Priorities: 1. Mobile-first and responsive. 2. Simple preference entry.
3. Strong visual destination discovery. 4. Clear distinction between
estimated and verified information. 5. Accessible controls and
reduced-motion support. 6. Fast, calm interaction rather than excessive
gamification.

## 2. Information architecture

Primary navigation: - Home - Explore Kerala - How it works - About

Utility navigation: - Saved trips (guest-local initially) - Install app
(when installable) - Contact - Privacy - Terms

Main routes:

| Route | Screen |
|---|---|
| `/` | Homepage |
| `/plan` | Preference wizard (5 steps + review) |
| `/trip/:tripId` | Three recommendations (or the fewer-than-three state) |
| `/trip/:tripId/roulette` | Roulette |
| `/trip/:tripId/destination` | Chosen destination with trip-specific costs, itinerary and access info |
| `/destinations/:slug` | Public destination page (no trip context) |
| `/shared/:token` | Shared trip view |
| `/explore` | Curated destination discovery |
| `/saved` | Saved trips (stored locally) |
| `/how-it-works`, `/about`, `/contact`, `/privacy`, `/terms` | Content pages |
| `/admin` | Protected admin area |

## 3. Main user flow

``` mermaid
flowchart TD
    A[Homepage] --> B[Start Your Trip]
    B --> C[Preference Wizard]
    C --> D{Inputs valid?}
    D -->|No| C
    D -->|Yes| E[Generate recommendations]
    E --> F{Three eligible results?}
    F -->|No| G[Explain constraint conflict]
    G --> C
    F -->|Yes| H[Three recommendation cards]
    H --> I[Review destinations]
    I --> J[Spin roulette]
    J --> K[Server-selected destination]
    K --> L[Destination details]
    L --> M[Itinerary and cost estimate]
    M --> N[Save or share]
```

## 4. Screen specifications

### Screen 1 --- Homepage

Purpose: Explain the value proposition and start the journey.

Content hierarchy: 1. Brand and navigation. 2. Hero headline: "Don't
know where to go? Let Kerala surprise you." 3. Supporting sentence
explaining budget, time and mood-based discovery. 4. Primary CTA: "Start
Your Trip". 5. Secondary CTA: "Explore Destinations". 6. Curated
destination cards. 7. "How it works" three-step explanation. 8. Trust
section explaining estimates and destination verification. 9. Footer.

UX rules: - Do not place the entire preference form in the hero. - Use
real, licensed destination photography. - Keep primary CTA visible
without excessive scrolling on common mobile sizes. - Avoid auto-playing
video.

### Screen 2 --- Preference wizard

Purpose: Collect enough information to make useful recommendations
without overwhelming the user.

Suggested step structure:

**Step 1: Starting point** - Searchable city/town/location field. -
Optional browser geolocation, only after explicit user action and
permission. - Show selected location clearly. - Allow manual search if
geolocation is denied.

**Step 2: When and how long** - Specific date or flexible date. -
Duration: few hours, one day, two days, three to five days. - Explain
that exact-date recommendations may use access and weather data where
available.

**Step 3: Budget and travellers** - Budget per person (INR). - Preset
chips plus custom amount. - Number of travellers. - Group type: solo,
friends, couple, family. - Make "per person" explicit near the amount.

**Step 4: Travel mood** - Multi-select interest cards with icon and
label. - Example taxonomy: nature, beach, adventure, culture,
relaxation, wildlife, food. - Require at least one interest.

**Step 5: Travel preferences (optional)** - Bike, car or public
transport. - Overnight accommodation preference when relevant. -
Accessibility needs only if supported by reliable destination records.

Actions: - Back. - Continue. - Review and find destinations.

Behaviour: - Preserve wizard state when navigating backward. - Validate
inline. - Display a progress indicator. - Do not silently change
inputs. - Provide a clear review summary before submission.

### Screen 3 --- Recommendation results

Purpose: Help the user understand the three options before spinning.

Content: - Summary of user preferences. - Exactly three destination
cards. - Image, name, district and experience type. - Distance and
travel time if supported. - Estimated per-person budget. - Match
explanation. - Warnings and data freshness. - CTA: "Spin to choose". -
Secondary action: "Adjust preferences".

Card design: - Use a strong image but avoid text over busy image
areas. - Put price and distance in readable text, not image overlays. -
Use labels such as "Estimated" and "Last checked". - Never show an
unexplained match score as if it were an objective rating.

### Screen 4 --- Roulette

Purpose: Provide a fun, fair reveal.

Elements: - Three destinations represented on the wheel. - Clear Spin
button. - Short instruction that each option has equal probability. -
Reduced-motion alternative. - Loading and error states. - Result
announcement after animation.

Interaction: 1. User activates Spin. 2. Button is disabled while request
is pending. 3. Client requests server spin with an idempotency key. 4.
Server returns selected destination and result identifier. 5. Wheel
animates to the returned destination. 6. Result is announced accessibly.
7. CTA opens destination details.

Do not select a winner in the browser. Do not let the wheel animation
decide the winner.

### Screen 5 --- Destination detail

Content order: 1. Hero image and destination title. 2. District,
category and short overview. 3. Key travel facts: distance, estimated
travel time, suggested duration. 4. Cost estimate with itemized
breakdown. 5. Attractions and activities. 6. Suggested itinerary. 7.
Route/map link. 8. Access, permit, seasonal and safety information. 9.
Sources and last-verified dates. 10. Save/share actions.

Sticky mobile CTA may be used for "View itinerary" or "Share trip", but
must not obscure content.

### Screen 6 --- Shared trip

-   Show destination, preference summary, estimate and itinerary.
-   Clearly identify the content as a shared plan, not a booking.
-   Do not expose private account information.
-   Allow the viewer to start their own trip.
-   Handle expired or revoked share links gracefully.

### Screen 7 --- Admin

-   Dashboard with draft, published and review-needed destinations.
-   Search and filter destinations.
-   Destination editor with validation.
-   Attraction, cost, image and access-information management.
-   Source URL, source type, verification date and review-due date.
-   Preview before publish.
-   Audit trail for important edits.

## 5. Visual design direction

Suggested visual personality: - Fresh, welcoming, outdoors-oriented. -
Kerala-inspired without relying on clichés. - Strong destination
photography. - Clean typography and generous spacing. - Calm neutral
surfaces with a restrained green accent. - Warm accent colour for the
roulette action. - Consistent iconography.

Avoid: - overly childish game styling; - excessive gradients and glass
effects; - dense travel-booking dashboards; - tiny price and disclaimer
text; - fake ratings or unverified popularity indicators.

## 6. Responsive behaviour

### Mobile

-   Single-column layout.
-   Wizard controls sized for touch.
-   Bottom-aligned primary action where appropriate.
-   Cards stack vertically.
-   Map opens as a dedicated view or external map app.
-   Roulette remains usable without horizontal scrolling.

### Tablet

-   Two-column destination cards where space permits.
-   Wizard content constrained to a readable width.

### Desktop

-   Wider hero and destination imagery.
-   Three recommendation cards in a row where suitable.
-   Detail pages may use main content plus a sticky summary panel.
-   Keep text line length readable.

## 8. UX states to design

For every screen, include: - initial/loading; - success; - empty; -
validation error; - network error; - unavailable external service; -
stale data; - permission denied; - offline; - mobile narrow viewport; -
keyboard-only interaction.

Special cases: - fewer than three eligible destinations; - no route
estimate; - missing cost information; - destination access not recently
verified; - spin request times out after server may have completed; -
share link expired; - user reloads after receiving a spin result.

## 9. Accessibility requirements

-   Semantic HTML and heading hierarchy.
-   Every input has a visible label.
-   All interactive controls are keyboard accessible.
-   Focus is visible and managed after wizard step changes.
-   Roulette result is announced to assistive technology.
-   Reduced-motion preference disables or simplifies animation.
-   Contrast meets WCAG 2.2 AA targets where applicable.
-   Images have useful alt text; decorative images have empty alt text.
-   Errors are described in text, not only colour.

## 10. Content and trust language

Preferred labels: - "Estimated cost" - "Approximate road distance" -
"Travel time estimate" - "Last verified" - "Access information
unavailable" - "Check the official source before travelling"

Avoid: - "Guaranteed open" - "Exact cost" - "Definitely safe" - "Best
destination" without a defined and defensible basis.

## 11. Design deliverables

Before implementation: 1. Sitemap. 2. User flow diagrams. 3.
Low-fidelity wireframes for all primary screens. 4. High-fidelity mobile
and desktop designs. 5. Clickable prototype. 6. Component and token
library. 7. Responsive and accessibility annotations. 8. Usability
review with representative travellers.

## 12. Usability test tasks

Ask 5--8 target users to attempt: 1. Find a one-day trip from their town
under a stated budget. 2. Understand why each destination was
recommended. 3. Spin and identify the selected destination. 4. Find the
total estimated cost and what it includes. 5. Identify whether access
information is verified. 6. Share the trip with a friend.

Observe completion, hesitation, errors and misunderstandings. Do not
lead users through the tasks.
