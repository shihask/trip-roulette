# Trip Roulette Kerala --- Test Plan & Quality Strategy

**Document version:** 1.2 (security, RLS and access-policy tests aligned with Architecture 1.2)\
**Date:** 4 November 2026\
**Status:** Initial QA baseline; detailed test cases to be expanded
alongside implementation

------------------------------------------------------------------------

## 1. Purpose

This document defines how Trip Roulette Kerala will be verified before
beta and public release. Testing must cover not only whether screens
work, but whether recommendations, cost estimates, access information
and roulette outcomes are trustworthy.

## 2. Quality objectives

-   Correct preference validation.
-   No recommendation that violates a hard constraint.
-   Exactly three recommendations on a successful recommendation
    response.
-   Honest handling when fewer than three destinations qualify.
-   Fair, server-authoritative roulette selection.
-   Transparent cost estimates.
-   No unsupported claims about opening hours, access or permits.
-   Safe guest sharing and admin authorization.
-   Responsive, accessible and performant PWA.
-   Regression protection for previously working behaviour.

## 4. Functional test scenarios

### 4.1 Homepage

-   Homepage loads on mobile and desktop.
-   Primary CTA opens the wizard.
-   Navigation links work.
-   Images have appropriate alt text and load responsively.
-   No layout overflow at narrow widths.

### 4.2 Preference wizard

-   Required fields cannot be skipped.
-   Budget must be a positive valid amount.
-   Traveller count must be within configured bounds.
-   At least one interest is required.
-   Starting location must resolve to a supported location.
-   Specific date and flexible date states behave correctly.
-   Past dates are rejected for planned trips, while flexible
    exploration remains possible.
-   Back navigation preserves values.
-   Refresh behaviour is defined and tested.
-   Keyboard and touch interaction work.
-   Location permission denial does not block manual search.

### 4.3 Recommendation engine

Test:

-   all constraints satisfied;
-   cost exactly equal to budget (passes);
-   budget one paise below cost (fails);
-   cost range whose upper bound exceeds the budget (fails);
-   one-way travel time exactly at the `duration_rules` limit, and one
    minute over;
-   duration not in `suitable_durations`;
-   unsupported or excluded transport mode;
-   destination archived or draft;
-   essential access record `closed` on the travel date (excluded);
-   essential access record past `review_due_at` (excluded);
-   no essential access record covering the date (excluded);
-   essential access `restricted` (eligible with warning);
-   non-essential access stale or missing (eligible with warning);
-   access validity boundary dates;
-   flexible date with a closure inside / outside the 14-day window;
-   missing essential cost data (excluded);
-   missing route data (excluded);
-   duplicate and highly similar candidates (diversity);
-   fewer than three eligible destinations, with correct relaxation
    counts that never relax the essential-access rule;
-   large candidate pool;
-   multiple moods;
-   changing the active `algorithm_configs` version changes scores
    without code changes, and stored recommendations keep their
    original version.

Assertions: - successful response contains exactly three unique
destinations; - every result satisfies configured hard constraints; -
all result IDs belong to the stored recommendation set; - score
components and algorithm version are recorded; - diversity policy is
applied predictably; - insufficient results are returned honestly; - no
AI-generated destination can enter the result unless it exists and is
eligible in the database.

### 4.4 Roulette

-   Only the three recommendation IDs can win.
-   Server determines the winner.
-   Frontend animation lands on the returned winner.
-   Each of three destinations has equal theoretical probability.
-   Repeated test runs show no obvious selection bias; statistical tests
    are diagnostic, not proof of cryptographic correctness.
-   Client cannot submit a destination ID as winner.
-   Double-click does not create two results.
-   Network retry with the same idempotency key returns the same result.
-   Concurrent spin requests create at most one stored result.
-   Refresh after a completed spin shows the same result.
-   Reduced-motion mode still communicates the winner.
-   API failure does not show a false winner.

### 4.5 Destination details

-   Correct destination slug resolves.
-   Archived or unpublished destination is not exposed publicly.
-   Image attribution is displayed where required.
-   Cost totals reconcile with line items.
-   Unknown values are shown as unknown.
-   Stale verification dates are visible.
-   Access warnings are visible and understandable.
-   Map links use the correct coordinates.
-   No fake rating, fee or opening time is displayed.

### 4.6 Cost calculation

Test: - fuel formula with known distance and mileage; - vehicle cost
divided across traveller count; - per-person food amount; - per-person
entry fee; - group parking/toll amount; - accommodation divided by room
occupancy; - missing fuel price; - missing route distance; - cost range
input; - currency conversion not supported or unavailable; - rounding to
paise/rupees; - group size changes; - estimates at budget boundary.

Use integer minor units or decimal arithmetic. Verify the displayed
group total and per-person total against independently calculated
expected values.

### 4.7 Itinerary

-   Total itinerary fits the selected duration.
-   Travel buffers are included.
-   Meal/rest breaks are included where appropriate.
-   Closed attractions are excluded for the selected date when verified.
-   Unknown opening information produces a warning, not an invented
    time.
-   Attraction order and route durations are consistent.
-   Empty attraction list returns a useful fallback.
-   AI provider failure returns a deterministic fallback or explicit
    unavailable state.
-   Generated itinerary is labelled as suggested, not booked.

### 4.8 Save and share

-   Guest can save a trip locally.
-   Saved trip survives expected browser restart behaviour.
-   Share link opens the intended snapshot.
-   Share token is unguessable.
-   Revoked and expired links fail safely.
-   Private user data is not exposed.
-   Shared trip cannot be edited by an unauthorized viewer.
-   Copy and native share fallbacks work.

### 4.9 Admin

-   Non-admin cannot access admin APIs.
-   Admin can create and edit draft destinations.
-   Publish validation blocks missing required fields.
-   Source and verification dates are required for controlled claims.
-   Material edits create audit records.
-   Image upload validates type and size.
-   Archive operation preserves historical trip references.

## 5. Security test scenarios

-   Anonymous user cannot read another user's private trip.
-   User A cannot update User B's trip.
-   Client cannot assign itself an admin role.
-   Service-role key is absent from frontend bundles.
-   Share token brute-force resistance is reviewed.
-   Rate limits apply to expensive endpoints.
-   Input payloads are validated and size-limited.
-   SQL injection and stored XSS risks are checked.
-   Image upload and external URL handling are validated.
-   CORS and security headers are configured.
-   Logs do not contain secrets or unnecessary precise location.
-   RLS is tested directly against the database (pgTAP) for `anon`, an
    anonymous user, another user, the owner, `editor` and `admin` —
    not only through UI hiding.
-   No client role can insert, update or delete `trips`,
    `trip_recommendations`, `roulette_results`, `trip_itinerary_items`
    or `trip_share_links`.
-   Another user's trip ID returns no rows (direct read) and
    `404 TRIP_NOT_FOUND` (functions).
-   An anonymous user cannot gain admin rights, even if added to
    `admin_users`.
-   Anonymous sign-in is protected by CAPTCHA and rate limits.
-   The service-role key is absent from the Next.js bundle and Vercel
    environment.
-   `token_hash` is not readable by clients.

## 6. PWA and compatibility tests

Test on: - current Chrome desktop; - current Edge desktop; - Android
Chrome; - iOS Safari and supported installed-PWA behaviour; - common
tablet viewport sizes.

Scenarios: - install prompt or browser install path; - app icon and
manifest; - offline access to cached public content; - stale-data
warning; - service-worker update; - network loss during recommendation
request; - network loss during spin request; - reconnect and retry; - no
private data leakage through caches.

## 7. Accessibility tests

-   Full keyboard navigation.
-   Focus visibility and logical order.
-   Screen-reader labels for form controls.
-   Error messages associated with fields.
-   Result announcement after spin.
-   Reduced-motion support.
-   Text contrast.
-   Zoom and text resizing.
-   Touch target size.
-   Images have appropriate alternative text.

## 8. Performance tests

Measure: - homepage first load on mobile network; - wizard interaction
responsiveness; - destination detail image loading; - recommendation
endpoint latency; - spin endpoint latency; - itinerary generation
latency; - database query plans; - service-worker cache behaviour.

Use realistic images and representative destination data. Set numeric
performance budgets after measuring a baseline on target devices and
networks. Avoid claiming performance targets are met until measured.

## 9. Regression strategy

For every behaviour change: 1. Inspect the existing implementation. 2.
Trace affected user flows, calculations, database queries and API
contracts. 3. Identify edge cases and backward compatibility concerns.
4. Add or update tests before or alongside the change. 5. Run relevant
unit, integration and end-to-end tests. 6. Review database migrations
and rollback implications. 7. Compare expected behaviour with actual
behaviour. 8. Record any intentional behaviour change.

Maintain regression suites for: - recommendation eligibility; - budget
calculations; - roulette idempotency; - access restrictions; - guest
sharing; - RLS; - PWA caching.

## 10. Test data strategy

Create separate datasets for: - valid published destinations; - draft
and archived destinations; - stale verification records; - open,
restricted, closed and unknown access states; - complete and incomplete
cost data; - destinations with and without routes; - duplicate and
similar candidates; - multiple categories and attraction counts.

Clearly mark sample data. Never allow placeholder values to appear as
verified production information.

## 11. UAT plan

Recruit 5--8 representative testers across friends, couples, families
and solo travellers.

Give them these tasks without coaching: 1. Find a one-day trip from a
selected Kerala town within a stated budget. 2. Explain why the three
destinations match. 3. Spin and identify the winner. 4. Find the
per-person cost and assumptions. 5. Check whether access information is
current. 6. Generate an itinerary. 7. Share the trip with another
person.

Record: - task completion; - time to complete; - confusion points; -
incorrect assumptions; - trust in cost/access information; - likelihood
of using or sharing the product.

Fix high-severity usability issues before public launch.

## 13. Release gates

### Private beta

-   Core journey passes.
-   Recommendation and roulette tests pass.
-   RLS and admin authorization reviewed.
-   No known critical or high defects.
-   Destination data has editorial review.
-   Monitoring and rollback path exist.

### Public release

-   Beta feedback triaged.
-   Performance and accessibility reviewed.
-   Privacy and legal pages published.
-   Production backups and migration process confirmed.
-   External provider quotas and failure handling tested.
-   Support/contact path available.

## 14. Test reporting template

defect references; - severity; - release recommendation; - tester.
